# Floor Frame — React Native / Viro

An iPhone comparison app using **@reactvision/react-viro 3.0.3**, **Expo 57.0.31**, **React Native 0.86.3**, and **React 19.2.3**. It installs as **Floor Frame Viro** (`cz.koval.floorframe.viro`) alongside the Swift/RealityKit **Floor Frame** app.

Expo 58 is available, but Viro 3.0.3 declares Expo `>=57 <58` and RN `>=0.86 <0.87`. The package lock preserves this supported stack. The app opts into Expo 57’s supported `expo-build-properties` `ios.enableSceneSupport` option, required when building with Xcode 27 for iOS 27. No Expo Go: Viro and the local session module require a native build.

## Match to the Swift app

- Same portrait camera view, center target, status wording, dark blurred controls, size selector, reset, and anchor/reposition workflow.
- Small block: **20 × 9 × 10 cm**. Large block: **3 × 1.35 × 1.5 m**. Dimensions are width × depth × height.
- Same mint color, PBR roughness 0.6, 60% opacity, opaque red bounding edges, and proportional rounded corners. The rounded OBJ uses the same physical dimensions and radius, although mesh tessellation and shading differ between engines.
- Same 20 Hz surface-preview budget, projected viewer-facing wide edge, local surface slope, 60° incline limit, below-camera check, and 8 m range limit. Invalid hits hide the preview and disable anchoring.
- Real ARKit anchor on placement; subsequent native anchor transforms drive the Viro node. Width can change after anchoring. Reposition removes the anchor. Placements are session-only.
- LiDAR mesh defaults on when supported, is unavailable on non-LiDAR devices and while anchored, and resets scanning when switched. Off uses standard ARKit detection. This does not disable sensor hardware.

## Architecture and comparison limits

**Viro renders the 3D scene and camera; React Native renders the controls.** The local Expo module in `modules/floor-frame-session` locates Viro's existing ARKit session. It never creates another session, camera view, RealityKit view, or renderer. It applies the same ARKit configuration as Swift, samples a center `.estimatedPlane / .any` raycast, and adds/removes an ARAnchor. The surface-facing calculations run in TypeScript and match `../FloorFrame/SurfacePose.swift`.

This bridge is needed because Viro's stock hit-test API and generic anchor attachment do not expose the exact behavior used by the Swift app. Viro's separate depth, collision-world-mesh and occlusion features remain off: the switch controls ARKit scene reconstruction directly, matching the Swift baseline without adding monocular inference or physics work.

This is a comparison of **React Native + Viro + a small ARKit bridge versus SwiftUI + RealityKit**, not an isolation of JavaScript overhead. RealityKit and Viro use different renderers, lighting, transparency sorting, mesh tessellation, and text/icon rendering. The Viro scene uses ambient/directional lighting; RealityKit uses its lighting environment. Visual output cannot be pixel-identical. UI icons are text glyphs in the RN version. No performance winner or measured FPS is asserted.

## Run

From this folder:

```sh
npm ci
npm run prebuild
cd ios && pod install && cd ..
npm run ios:release
```

The config includes this Mac's signing team; change `ios.appleTeamId` in `app.json` for another account. `ios/` is generated by Expo prebuild. The local native module, app configuration, Metro asset extensions, lockfile and OBJ generator are reproducible source inputs.

For development, `npm run ios` builds a device Debug app. `npm start` runs Metro. Performance comparisons should use Release builds, without Metro, JS debugging or screen recording.

```sh
npm run typecheck
npm test
npx react-doctor@latest --verbose
```

The seven geometry tests cover the Swift scenarios plus Viro Euler-angle roundtrips, including the camera-facing gimbal case. Regenerate the rounded block with `python3 scripts/generate-block.py`.

## Repeatable manual comparison

Use the same iPhone, lighting, screen brightness, battery/charging state, and starting position. Let the device cool before each run. Run both apps in **Release**; the native app's earlier installed Debug build is not a fair baseline.

For each app, test small/large × mesh off/on separately:

1. Reset the scan. Slowly scan the same floor for 20 seconds.
2. Aim at the same spot and move along the same path for 30 seconds while the preview follows.
3. Anchor and walk the same path around it for 30 seconds.
4. Reposition, aim at the same incline, then anchor again.
5. Alternate app order across at least three runs.

Record time to first valid surface, preview jitter, anchor drift, visible frame pacing, CPU, memory, GPU load and thermal state. Instruments can attach to each standalone app; use the same instrumentation for both and report preview versus anchored phases separately. The React Native bridge continues to sample anchor updates at 20 Hz after anchoring, while the native anchor entity updates inside RealityKit; that is a real architectural difference in this implementation.

Argent can inspect the physical iPhone UI, but its Metro debugger/profiler does not support physical iPhones. A simulator cannot validate camera tracking, LiDAR or on-device AR performance. Actual AR acceptance requires moving the phone in the room.

To rebuild and install both Release apps after setup, run `scripts/install-comparison.sh IPHONE_UDID` from the parent project folder.

## Validation on 2026-10-22

- Both native and Viro iPhone Release builds succeeded and were installed side by side on the connected iPhone 16 Pro (iOS 27.2).
- TypeScript checks and all seven placement/Euler tests passed; React Doctor full scan: 100/100.
- Argent verified successful app launch and camera permission, full-screen HUD layout, switching to 3 m and back to 20 cm with correct dimension labels, LiDAR off/on with matching status labels, reset, and disabled anchoring while tracking is unavailable.
- Fixed Expo 57's iOS 27 launch lifecycle using its supported `enableSceneSupport` option. Wrapped the Viro navigator in an absolute-fill parent because Viro 3.0.3 ignores the passed navigator style.
- Live follow-up: once the phone was aimed at a lit floor, the camera feed, transparent rounded block (before the red-outline update), valid surface detection, and enabled Anchor button were verified. The user tapped Anchor and confirmed that the block stayed fixed while moving the phone. A subsequent Argent capture showed “Anchored in place”, the Reposition button, and the block displaced from the center target. A deliberately inclined surface and live Reposition remain unverified. No FPS/CPU/GPU performance results have been recorded.

Follow-up live check: after the phone was aimed at a lit parquet floor, Argent captured a rendered transparent small block, a valid surface about 1.1 m away, a reported 3° local slope, and the enabled Anchor button. This confirms the camera feed, ARKit session bridge, live surface hit, and Viro mesh rendering. A reported near-flat slope does not verify a deliberately inclined surface. Automated tapping waits for quiescence during continuous AR preview, the user then confirmed that the anchored block stayed fixed when moving the phone, and an Argent screenshot verified the anchored UI state. This is a functional check, not a drift measurement.

Argent taps can overrun their watchdog while the AR scene continuously updates. Automated live resizing/reposition checks were stopped without changing the app; those paths should be checked manually. The app was left running with the confirmed 20 cm placement anchored.

Both apps now outline all 12 bounding-box edges in opaque, unlit red. Bars are 3 mm thick at 20 cm width and 3 cm thick at 3 m width. Bars stay within the exact box extents, so their lower faces are 1 mm above the sampled surface; the outline itself does not extend below the block and falsely suggest sinking. The transparent mint body remains at 60% opacity.

Red-outline update validation: both Release builds, TypeScript, and React Doctor (100/100) passed. Both updated apps were installed and launched with Argent. Live outline appearance was not verified during this check because the camera saw a dark scene and tracking stayed limited.
